# Calculator attribute criteria

Review the bug details, profiles, and comments to assess:
- *Platforms* (`--platforms`) The platforms where the bug is known to occur. That normally includes the platform the reporter hit it on, taken from what they describe (their user agent, OS, or device), not from the OS / Platform field, which is often left at a single-OS default. Add other platforms only when someone reports or reproduces it there, or the cause is clearly platform-independent. The exception is when the OS / Platform field itself reads `All`: that value is never a default (a default is a specific OS, typically Windows) and requires someone to have deliberately selected it, so treat it as a genuine signal the bug applies across platforms. Leave it empty only when the bug gives no platform information.
- *Resource impact* Only specify if resource use is a PRIMARY concern, not a side-effect
- *Configuration* Can refer to uncommon hardware, uncommon feature usage, or unusual browser state (hundreds of tabs, long runtime, etc.)
- *Reproducible locally* (`--reproducible`) Refers to engineers/agents having been able to reproduce. STR or the reporter reproducing is not relevant — this holds even when the reporter has an @mozilla.com address and is QA or an engineer: filing the bug by following their own STR is still the reporter reproducing, not a separate confirmation. This flag is strictly for whether an engineer or QA has indicated they can reproduce the bug locally. The @mozilla.com rule below applies only to someone other than the reporter. Three states, and the distinction between the last two matters:
  - `reproduced` — an engineer or QA other than the reporter says they reproduced it locally. If a user with an @mozilla.com address who is not the reporter has reproduced it, treat that as reproduced.
  - `not-reproduced` — an engineer or QA says they **tried and could not** reproduce it. This requires positive evidence of a failed attempt, not merely the absence of a confirmation.
  - `not-attempted` (default) — nobody has said either way. Use this whenever the bug is silent on reproduction; do NOT infer `not-reproduced` from silence.
- *Multiple reporters* (`--multiple-reporters`) Means **multiple people independently hit and reported the bug**, e.g. duplicate bugs filed against it, several commenters saying they see it too on their own machines, or a bug filed on behalf of many users. It is NOT "a bunch of people commented on the bug" — a long discussion among engineers, triagers, or a single reporter going back and forth is still one reporter. It is also NOT an engineer confirming they can reproduce it; that is `--reproducible reproduced` and nothing more. Do not set this flag on the strength of comment volume alone; if you cannot point to distinct people independently encountering the bug, leave it off.
- *Multiple sites* (`--multiple-sites`) The same root cause reported on multiple sites, typically across separate bugs. Several hostnames mentioned inside one report is not enough.
- *Websites affected* (`--pages-affected`) Not a count of sites named in the bug — a measure of how popular/high-traffic the affected site(s) are, i.e. how much of our user population would notice if this site had a problem. `major` means a top-50-class site (named explicitly in the calculator as the `top50` case): a single such site named in the bug is enough, regardless of how many sites total are mentioned. `rare` is the opposite end: a site obscure enough it would barely register in aggregate metrics. Use `unclear` when the bug does not give enough information to judge the named site's popularity; it scores the same as `common` (×1) but records that the input was unknown rather than assessed, so prefer it over guessing `common`. This is independent of `--multiple-sites`, which is about whether the same root cause recurs across more than one site, not how popular any one of them is.
- *Page load impact* (`--pageload-impact`) Strictly about delay during the page's own initial load or navigation — not post-load interaction, scrolling, or resource-usage jank, even when the bug's text happens to contain the word "load" or "navigate" in an unrelated sense.
  - `none` (default) — no reported load/navigation delay, or the complaint is about something after the page has already loaded.
  - `some` — a load/navigation delay reported as a small, specific relative difference (e.g. "10% slower", "100-200ms slower than Chrome").
  - `severe` — a load/navigation delay that is large, open-ended, or unbounded (multiple seconds or more, "very slow", "frequent long janks" on load, no numeric bound given beyond "slow").

  Leave it at `none` when the delay is a clear downstream symptom of a different primary cause that is already scored elsewhere (e.g. pages hanging specifically because another process is saturating the CPU, scored under `--resource-impact`/`--configuration` instead) — scoring it again under page load impact double-counts the same root cause.
- *Animation* Only for web-driven animated content, NOT browser UI (scrolling, resizing, tab switches)
- *Impact on browser* This is strictly for when the browser UI is affected, not just because a website is slow.
- *Impact on site*
  - `minor` (default) — a slowdown or jank a user could easily miss or shrug off: barely perceptible, or perceptible but not disruptive to what they're doing.
  - `noticeable` — degraded but still interactive: laggy scrolling, low frame rate, a page that feels slower or janky throughout, but the user can keep working with it the whole time.
  - `major` — the page stops responding entirely for a span of multiple seconds or more (blank screen, frozen UI, input not registering, "stuck") before recovering, rather than merely being slow or janky the whole time. Treat this as the bar even when it clears up on its own and even if the report doesn't call the site literally unusable — a user hitting a several-second dead stretch is what this tier is for. A site is also `major` if it is janked so severely a user cannot get anything done on it at all, or a page never finishes loading (stuck indefinitely, not merely slow); in the latter case leave page load impact at its default, to avoid double-counting.

  When the whole browser hangs or freezes, use `--site-impact minor`: the hang is scored by browser impact, and counting it again for the site double-counts it.
- *Reproduces in Chrome* (`--chrome`) Set only when someone reports that the same problem also happens in Chrome. A report that Chrome is fine, or faster, is the opposite and means leaving it off. Silence means leaving it off.
